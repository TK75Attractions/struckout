## 1. 目的と期待する動作

**目的**: カメラアプリの検出が、飛んでいる色つきのボールを「色がない」と判断して捨てるのを直す。

**期待する動作**

- ぶれて写ったボールも、明るい背景の前のボールも検出として残る。2026-10-10 の録画で、手で選んだボールのコマ 161 個 (左 83、右 78) をすべて残す。今は 116 個で、青いボール (1・2 球目) は 42 個のうち 1 個しか残らない。
- 影と、明るさだけの変化は、面の色に関係なく捨てる (茶色い箱に落ちた影は今は通っている)。ボール以外の検出は今より増やさない。
- 変えないもの: 差分の取り方、二値化、モルフォロジー、輪郭、背景の更新、検出の位置と大きさ (bbox)、通信、設定画面。
- 2 つのアプリと `detect_objects.py` が同じ判定をする。

### 2.2 原因は「背景に残った跡」ではなく、露光中のぶれ

依頼時の前提 (`recordings/2026-10-10/notes.md` の「検出」の節) は「背景に 1 コマ前のボールの跡が残り、今のボールとつながる」だった。コードも録画もこれを支持しない。

- **コード**: 前景と判定した画素は背景の更新から外している (上の表)。跡を残さないための修正がすでに入っていて (commit `17d76b3`)、`ObjectTrackerInstrumentedTest.movingObjectDoesNotLeaveGhostContours` がそれを確かめている。
- **録画** (左 1 球目・3 球目、右 1 球目のボールのかたまり 21 個)。投球前 50 コマの中央値を「きれいな背景」として比べた。
  - かたまりの画素の 98〜100% は、今のコマ自体がきれいな背景と 15 階調を超えて違う。
  - 背景モデルがきれいな背景と 15 階調を超えて違う画素は、かたまりの 0〜3% しかない。
- かたまりが大きいのは、ボールが露光中に動いて筋になっているため。左 1 球目 (コマ 2449、bbox 339,86,56,68) では、幅約 32px のボールが 1 コマに約 40px 動き、色の変化が進行方向に約 76px 続く。露光は 1 コマの間隔 (1/60 秒) にほぼ等しい (かたまりの形からの推定。動画の記録では未確認)。
- 筋の中の画素は、ボールの色と背景の色が混ざっている。同じかたまりで、中心の画素は (5, 39, 102) で彩度 0.95 あるのに、輪郭内の平均色の彩度は 0.22 しかない。
- KYV45 の 30fps の録画でも、かたまりは露光中のぶれで 100〜250px ある (`recordings/2026-10-07/notes.md:121-122`)。

したがって「今の物体と跡を分ける」という直し方は成り立たない。分ける相手がない。

### 2.3 彩度で判定することの限界

輪郭内の平均色は「薄まったボール + 透けた背景 + そばの影」の色で、ボールの色ではない。その彩度は背景の色で決まってしまう。

- 白い天井や明るい壁の前では、ボールが鮮やかでも下がる。青いボールの 42 コマは 0.05〜0.29 で、41 コマが 0.25 未満。
- 色のついた面の上では、影でも高くなる。茶色い箱の影 5 コマは 0.52〜0.61。

知りたいのは「色のついた物体が来たか」で、これは今のコマの色だけでは決まらない。背景からの色の変わり方で決まる。

### 3.2 採用する判定: 色みの変化

「輪郭内の平均色の彩度」をやめ、「輪郭内の平均色が、背景の同じ場所の平均色から、どれだけ色みを変えたか」で判定する。3 つの実装で次のとおりにそろえる。

```
mask       = 輪郭を塗りつぶしたマスク (今の saturation() と同じ作り方)
now        = mean(frame[bbox], mask)          // 3 チャンネル
before     = mean(background8[bbox], mask)    // このコマの差分に使った背景 (更新前を 8 ビットにしたもの)
k          = dot(now, before) / dot(before, before)    // 分母が 0 なら k = 0
scaleRes   = |now - k * before|               // (1) 明るさだけ変わったとみなしたときの残り
delta      = now - before
offsetRes  = |delta - (delta の 3 チャンネルの平均)|   // (2) 全チャンネル同じ量だけ増減したとみなしたときの残り
colorShift = min(scaleRes, offsetRes)         // 単位は 8 ビットの階調、|…| はユークリッド距離
残す条件: minColorShift <= 0 または colorShift >= minColorShift
```

- 影や照明の変化は、面の色に関係なく (1) がほぼ 0 になる。白・灰・黒の物体や露出の変化は (2) がほぼ 0 になる。
- 色のついたボールは、背景が透けて薄まっていても色みがずれるので値が残る。
- (1) だけにしない理由: 黒い背景に白い物体で (1) は 441.7 になり、既存テスト `minSaturationRejectsColorlessObjects` の意図 (色のない物体を捨てる) を守れない。(2) を合わせると 0 になる。同じ下限で比べると、(1) だけの場合よりボール以外が必ず少ない (12 で 328・147 → 241・131)。
- 画素ごとの方式より 10/07 で成績が良いのは、平均どうしを比べるので、揺れで縁がずれただけのかたまり (明るくなった画素と暗くなった画素が打ち消し合う) が小さくなるためと考えている (推定)。
- 追加の処理は、輪郭 1 個につき「背景の同じ範囲の平均」1 回と四則演算だけ。使う OpenCV の関数は今と同じ。チャンネルの並びには依存しない。

名前は Kotlin で `minColorShift`、定数 `MIN_BALL_COLOR_SHIFT`、Python で `min_color_shift`、オプション `--min-color-shift`、CSV の列 `color_shift` とする。

### 3.3 下限は 10 にする (試算)

| 下限 | ボール 10/10 (161) | ボール 10/07 (42) | ボール以外 10/10 | ボール以外 10/07 |
|---|---|---|---|---|
| 今の判定 | 116 | 40 | 594 | 348 |
| 8 | 161 | 41 | 334 | 246 |
| **10** | **161** | **41** | **298** | **178** |
| 12 | 161 | 41 | 241 | 131 |
| 14 | 161 | 40 | 202 | 121 |

- ボールのコマの値: 10/10 は最小 17.2 (赤いボールが茶色い面の前)、球ごとの中央値は 25〜68。10/07 は、落ちる 1 コマ (7.4) を除くと最小 14.0。
- 既知の影 (茶色い箱、左 1 球目の 5 コマ): 5.5〜7.4。
- 10 なら、ボールの最小値に対して 1.4 倍 (10/07)、1.7 倍 (10/10) の余裕がある。12 はボール以外をさらに 2 割ほど減らすが、余裕が 1.2 倍まで減る。この修正の目的はボールを捨てないことで、ボール以外への強さは ball_tracker 側の計画 (②) が扱うので、余裕を優先する。
- 両アプリで同じ値にする。定数のままにして、設定画面には出さない。

### 3.4 影と bbox の扱い

- **影**: この判定で扱う。色のついた面の影も捨てる。着弾前 0.45 秒のあいだのボール以外の検出は、10/10 で 36 → 4、10/07 で 18 → 12 に減る。10/10 に残る 4 個は、色と時刻から見て、着弾の瞬間や画角に入りかけたボール自身と思われる (未確認)。
- **残るもの**: 色のついた背景の前の白・灰・黒の物体 (人の服など)、跳ね返ったあとのボール、色が変わる照明。これらは ball_tracker 側の計画 (②) に任せる。
- **bbox と中心**: 変えない。除くべき跡がない。かたまりは露光中のボールの通り道なので、中心は露光の中ほどでの位置にあたる。時刻とのずれは検出では直せないので、7 章の引き継ぎに入れる。ball_tracker は bbox の大きさを使っていない (`ball_tracker/src` で `bbox_` が出るのはテストの値だけ)。

## 7. リスクと未決事項

**リスク**

- 下限 10 は 4 本の録画 (2 日、同じ筐体、1080p の動画を 640×360 に縮めたもの、iPhone 60fps と KYV45 標準カメラ 30fps) から決めた。アプリが実際に受け取る画像 (CameraX の YUV→RGB、120fps の GPU 縮小) と 120fps の素材では確かめていない。
- 値はぶれで薄まるほど小さくなる。30fps・速い球・くすんだ色が重なると 10 を下回りうる (録画での最小は 14.0。もっと速い球は未確認)。120fps ではぶれが 4 分の 1 になるので余裕は増える (推定)。
- 色が変わる照明 (プロジェクターの映像の切り替わりが壁や天井を照らす場合) は、今の彩度の判定より通りやすい。録画でプロジェクターが点いていたかは未確認。
- 背景と色みが同じボールは捨てる。背景の色をそのまま明るく・暗くした色 (茶色い木の前の橙色など) と、背景に灰色を足し引きした色が当たる。録画で最も弱かったのは、茶色い面の前の赤いボール (17.2)。
- 画像の端で切れた小さなかたまりは落ちやすい。10/07 で 1 コマ落ちる (7.4)。端で切れたコマは中心がずれているので、落ちて困るかどうかは ball_tracker 側と合わせて判断する。
- 10/07 のボールのコマは計画者が検出の並びから選んだ。映像では確かめていない。
- 既存の `recordings/2026-10-07/detections_cam_*.csv` は、今の `detect_objects.py` の結果と比べて 1 コマぶん (約 35ms) 時刻が遅い (同じ bbox が 1 コマ後に出る)。頭出しの方法を変える前の版で作られたためと思われる (推定)。10/07 との比較は、コマ番号ではなく作り直した CSV で行う。

**実装とレビューでわかったリスク (2026-10-12 追記)**

- 実装は手順 1〜4 まで済み、レビューで必ず直すべき指摘はなかった。Kotlin の `colorShift` のうち OpenCV を呼ぶ部分 (マスク、平均) は実機で一度も動かしていない。計算部分は PC 上で Python と一致することを確かめた。
- 既存テスト `minColorShiftRejectsColorlessObjects` は背景が黒なので、明るさの倍率の計算を通らない。古い判定でも同じく通るテストで、新しい判定を固定できていない。6.2 の表の下 2 行をテストに足せば固定できる (6.3、要了承)。
- 明るさだけの変化でも色みの変化は 0 にならず、変化の大きさの 1〜3 割が残る (既知の影は 5.5〜7.4 で、下限まで 1.35 倍)。影が濃いほど大きくなるので、白い壁や天井に落ちた濃い影は、古い判定では落ちていたのに通ることがある。録画ではボール以外の検出は全体で減ったが、新しく通るようになったものもある (10/10 の左で 86 件、多くは着弾後 1 秒以内)。
- 暗い背景の前では、ボールが背景と同じ色みで明るいだけだと捨てる (例: 背景 (4,5,9) の前の青 (40,55,95) は 3.1)。10/10 のボールのコマはすべて明るい背景の前だったので、録画では確かめられていない。筐体に暗い面が映るなら、倍率に上限を設けるなどの見直しが要る。
- 下限 10 で絞った検出結果は `recordings/2026-10-10/detections_{left,right}_colorshift10.csv` に置く (計画 ② の再生で使う)。
